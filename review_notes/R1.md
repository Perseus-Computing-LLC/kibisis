# R1 — laundering and fencing (round 1 review, head 74129f58ad45)

**Restatement.** Adversarially review the Python package `kibisis` (src/kibisis) at 74129f58ad45 through the cut
"can a stale lease holder, a replayed token, or a reordered call make a write the invariants forbid (incl. trust/provenance
laundering)"; prove each real, Python-fixable defect with a standalone failing test `tests/review1_<name>.py`, and record
the narrative here. Nothing is fixed; no existing file is edited.

**Assumptions not stated in the brief.**
1. The harness's fresh checkout runs with the same venv and the same prebuilt `kibisis_native` 0.1.0a17, and with the
   repo's unchanged `tests/conftest.py` and `pyproject.toml` (importlib mode).
2. Two `Vault`/coordinator objects opened on the same tmp_path files in one process are an acceptable model of two
   holders (two processes), since locks are file-based; where a real second process matters, `subprocess.run` is used.
3. Short real sleeps (about 2-3 s) to let a 1 s lease expire are acceptable ("sleeps only where lease expiry is the point").
4. "Current fencing token" means the token of the lease the coordinator currently records for the resource; a token
   from a released, expired, superseded, or different-resource lease is not current.
5. Tests open vaults with in-code options (plaintext/keyless or an explicit passphrase argument, as the existing tests
   do), never via environment variables.

## Findings

### F1 (high) — `set_persona_slot`: check and write in two transactions; a review that lands in between is erased
Test: `tests/review1_persona_slot_check_not_atomic.py` (red on head: 1 failed, 1 passed).

- `src/kibisis/vault.py:2544-2551` runs the protection check for a request from outside the principal class
  (`_refuse_if_protected`) inside its own `_write_tx()`; that transaction commits when the `with` block ends.
- `vault.py:2554-2567` then calls `self.put(...)`, which opens a second write transaction (`_put_journaled`).
  `_put_journaled` re-checks "reviewed" only for a capped write (`trust_ceiling`, `vault.py:1738-1744`). Only
  `origin="model"` implies the cap (`vault.py:1489-1493`). A `tool`-origin write (the one tested) over a same-class
  slot is therefore not re-checked under the lock it writes with. By reading the code, any other non-model,
  non-principal origin takes the same path. The class check at `vault.py:1652-1660` is atomic,
  but it does not look at reviews.
- Result: another connection commits a person's `verified` review between the two transactions. The tool's
  write then replaces the slot, and `human_reviews` is gone (the test shows content `"tool's profile v2"`, no
  reviews). Without the interleaving, the same call raises `ReviewedEntryError` (control test, green).
- Contract contradicted: `vault.py:2539-2542` (a non-principal request "cannot replace a slot a person verified
  or reviewed ... the same check tombstone runs"; tombstone/purge/archive check and write in one transaction), and
  the `_write_tx` contract at `vault.py:889-899` ("every mutating method enters this first so check-then-write is
  atomic against other connections").
- Determinism: the test wraps the agent vault's `_write_tx` and commits the review, through a second vault object
  on the same file, just before the agent opens its second outermost transaction. Under a fix (one transaction for
  check and write) the hook either fires before the check (refused) or not during the call (review applied after,
  survives); both pass.
- Python fix location: `vault.py:2544-2567`. Run the check and the `put` in one `_write_tx()` (it is re-entrant;
  `put` joins it). Alternatively, make `_put_journaled` apply the `_is_reviewed(existing)` refusal to every
  non-principal writer of the persona slot.

### F2 (medium) — `enforce_fencing`: origin/scope refusals are raised and journaled before the token is checked
Test: `tests/review1_refusal_journaled_before_fence.py` (red on head: 6 failed, 1 passed).

- Contract: `vault.py:333-336` says that with `enforce_fencing=True` "a missing, stale or expired token raises
  `LeaseConflictError` and changes nothing". `tests/test_enforce_fencing.py:3-6,47-53` counts the audit journal as
  part of what a refused call must not change.
- Three calls run an origin or scope check outside the fenced transaction, before any token is looked at. Then
  `_journal_protected_refusal` (`_vault_tombstone.py:114-131`) writes a `refuse` event in a fresh transaction:
  - `set_persona_slot(origin="model")` over a protected slot: `vault.py:2544-2551`. The fenced `put` comes only at
    `vault.py:2554`. Raises `ReviewedEntryError`.
  - `tombstone(scope="*", origin="tool")`: `_vault_tombstone.py:343-348`. The fence is in `_tombstone_locked`
    (`:373`). Raises `PermissionError`.
  - `lift_tombstone(origin="model")`: `_vault_tombstone.py:498-504`. The fence is in `_lift_tombstone_locked`
    (`:532`). Raises `PermissionError`.
- Result: after a takeover, the fenced-out holder (stale token), or a caller with no token at all, still adds one
  journal row per call. The row carries caller-chosen category, key, scope and author. The audit count goes 4 -> 5
  in each of the 6 parametrized cases, and the error is not `LeaseConflictError`. Entries and tombstones are not
  changed. The control test (green) shows that the same calls with a principal origin and a stale token are fenced
  and change nothing, and that the current holder's token works.
- Why medium rather than high: the brief's rubric makes "lease/fencing guarantee broken" high. But what leaks past
  the fence is only an audit record of the refused call itself, not entry or tombstone data. It is a wrong result
  (a journal write, and the wrong exception) under realistic misuse: a zombie holder relaying an agent's request.
- Python fix location: validate the fence before the origin/scope checks. In `_vault_tombstone.py:343-348` and
  `:498-504`, move the check into the fenced transaction or call `self._validate_fencing(...)` first. In
  `vault.py:2544-2551`, call `self._fence(cursor, ...)` in the pre-check transaction. Alternatively,
  `_journal_protected_refusal` (`_vault_tombstone.py:114-131`) records nothing when the call's fence does not pass.
  `purge` already uses the right order: it fences inside the same transaction, before its protection check
  (`_vault_tombstone.py:152-153`). The docstring of `_journal_protected_refusal` (`:117-118`) says refusals are
  journaled, but neither it nor any other comment says a refusal may come before the fence.

## Design questions (no test filed)

1. **The token works as a bearer number without `holder_id`, and no resource is bound to the vault.** In the holder-less
   path (`vault.py:857-866`), the only checks are "token == current token for the resource the caller names" and "not
   expired". The current token is a small integer that anyone can read with `coordinator.get_lease(resource)`, and the
   lease state is documented as not secret (`lease.py:58-59`). The vault also accepts a lease on any resource name
   (`vault.py:838-866`), so two writers that name different resources are not fenced against each other. Both
   behaviours are documented ("may pass `holder_id`", `vault.py:333-336`; SECURITY.md:22). Question: should
   `enforce_fencing` take a fixed resource and require `holder_id`?
2. **Entity origin from an unsealed snapshot is not capped at the importer's class.** I checked this with a probe.
   `import_snapshot({"entities":[{..., "origin": "user"}]}, origin="model")` planted a principal-class row. It also
   replaced a person's principal entry, which then kept `origin="user"`. A direct `put(origin="model")` over that
   entry raises `OriginClassError` (`vault.py:1652-1660`). Once planted, the model can no longer rewrite or tombstone
   the row. The code takes the file's origin at `_vault_snapshot.py:413-415` and passes it at `:454`. The cap applies
   only to tombstones (`:255-261`; SECURITY.md:307-312). SECURITY.md:305-307 and 314-316 and
   `_vault_snapshot.py:250-253,263-266` document this ("origin and author_id are restored as exported"; "a snapshot
   file is a trusted input for content"). Question: should a non-principal importer cap entity origin the same way it
   caps tombstones?
3. **A `tool`-origin `put` may replace a person-reviewed entry and drops `human_reviews`.** I checked this with a
   probe. Only `origin="model"` implies `trust_ceiling` (`vault.py:1489-1493`, docstring `:2017-2023`). This
   documented gap is what makes F1 reachable for `tool` requests.
4. **`record_refusal` (`vault.py:2183-2228`) is public and takes no token.** On an `enforce_fencing` vault, any caller
   appends `refuse` events. It does not add, change or remove entries, so it is outside the letter of
   `vault.py:333-336`.
5. **`migrate_plaintext` (`_vault_crypto.py:326-345`) and `adopt_unsigned_entries` (`:1363-1410`) take no fencing
   token** although they rewrite entry rows (re-seal or re-sign them). Not demonstrated: on this build, creating
   eligible rows (plaintext rows in a keyed vault, or unsigned legacy rows) needs a file edit, not the public API.

## Suspected, unconfirmed

- **`migrate_plaintext` reads outside the write lock** (`_vault_crypto.py:331-336`). It selects the plaintext rows with
  `self._conn.execute(...)` before `with self._write_tx()`. It then rewrites each row by id from that stale read
  (`_write_sealed`, `:367-375`, `UPDATE entities SET content = ... WHERE id = ?`), re-signed, so the result verifies. An
  update keeps the row id (`vault.py:1907-1909`). So a newer version that another connection commits between the
  SELECT and `BEGIN IMMEDIATE` would be overwritten with the older content (lost update). The older value could even
  be one tombstoned in between, because the tombstone gate is not re-checked. This contradicts the `_write_tx`
  contract (`vault.py:889-899`). It is not demonstrable through the public API here, for the reason in design
  question 5. Python fix: do the SELECT inside the `_write_tx()` block.
