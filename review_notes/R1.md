# R1 — atomicity and crash consistency

Cut: what state a fresh open can see after a kill between any two syscalls of a write path.
Head: `74129f58ad45` (detached). Every finding below has a repro `tests/review1_*.py` that exits 1 on
this head. Convention in each file: `test_control_*` asserts behaviour that holds (passes);
`test_attack_*` asserts the correct post-crash behaviour and FAILS because of the defect.

How a crash is modelled: a monkeypatched step between two syscalls of the write path raises a
`BaseException` subclass (`_Killed`), which stands in for the process dying at that point. Where
the code's own `except` handlers would run cleanup that a real SIGKILL never runs, the test either
kills a real child process (`os.kill(os.getpid(), SIGKILL)`) or says so explicitly.

## Findings

(appended per finding)

### R1-1 (high) — Argus mirror written before the vault transaction commits

Repro: `tests/review1_argus_before_commit.py` (2 failed, 1 passed).

`_record_state_transition` (src/kibisis/_vault_review.py:122-162) journals the transition into the
open SQLite transaction and then immediately calls `_argus_append` (src/kibisis/_vault_audit.py:46-55),
which appends (and locks/fsyncs) a record in the external Argus JSONL ledger. The SQLite COMMIT happens
later, when `_write_tx` exits (src/kibisis/vault.py:906-913). The two durable writes are ordered the
wrong way round for an audit mirror: anything that stops the transaction after the Argus append leaves
a ledger entry for a transition the vault never made.

- Kill between the Argus append and COMMIT (`test_attack_kill_after_argus_append_before_commit`): fresh
  open shows `facts:old` still `candidate`, no `state_transition` row in the vault journal, and the Argus
  ledger holds `candidate -> revoked` for it.
- No crash needed (`test_attack_refused_write_leaves_phantom_revocation`): in `_put` the supersession
  branch (vault.py:1806-1843, including `_record_state_transition` at 1836) runs before the tombstone
  check (vault.py:1847-1866). A supersession whose replacement holds a tombstoned value raises
  `TombstonedValueError` and rolls back, and Argus still records the revocation of the target. Same for
  every later raise in the transaction (`_cascade_invalidate`, sealing, journal append refusals).

Impact: the tamper-evident ledger, which SECURITY.md presents as the out-of-file record of state
transitions (SECURITY.md:184-187), attests revocations/verifications that never happened. A reader that
trusts Argus over the file is lied to, and nothing reconciles the two.

### R1-2 (high) — kill during the first open of a new keyed vault leaves a file that no longer opens

Repro: `tests/review1_first_open_brick.py` (1 failed, 2 passed).

A new vault is set up in several separate commits: `_init_schema` (vault.py:967, `with self._conn:`
commits the current-format tables, including `audit_head`, `audit_journal.format` and
`rejected_value_tombstones.tombstone_mac`), then `_vault_salt` commits `kdf_salt` alone
(_vault_crypto.py:305-317), then `derive_vault_keys` runs the 600,000-iteration PBKDF2 (vault.py:529),
and only after that does `_upgrade_integrity` -> `_upgrade_to_format_3` commit `integrity_format`,
`key_check` and `meta_mac` (_vault_crypto.py:932-978). The PBKDF2 stretch is a window of about half a
second to seconds in which a kill leaves salt + new schema + no key check.

Every later open refuses that file as tampered: `_refuse_unless_genuine_a5` sees a salt with no key
check, classes the file as an a5 candidate, and refuses it because the schema already has the later
tables (`VaultIntegrityError: ... it holds a table audit_head; ... the integrity records were removed`,
_vault_crypto.py:799). The correct passphrase does not help, and no flag recovers it. The vault held no
entries yet, so nothing is lost, but the file is unusable and the operator gets a false tamper alarm.
The control shows that a kill before the salt commit is harmless (the file is still a fresh vault).

### R1-3 (medium) — import_snapshot commits half of a refused per-entity write (nested `_write_tx` has no savepoint)

Repro: `tests/review1_import_nested_partial.py` (1 failed, 1 passed).

`_write_tx` (vault.py:888-913) yields the outer cursor when a transaction is already open
(vault.py:903-905): no SAVEPOINT, nothing undone if the inner block raises. `import_snapshot` runs its
whole restore in one transaction (_vault_snapshot.py:315) and calls `_put_journaled` per entity
(_vault_snapshot.py:445), catching `ReviewedEntryError`/`TombstonedValueError` per entity and carrying
on (_vault_snapshot.py:469-481). Statements an inner `_put` executed before it raised are not rolled
back. They commit with the rest of the import.

Concrete case: a foreign snapshot (no trust seal) that changes the content of a verified, attested
entry. `_put` journals `attestations_reset` ("content changed") at vault.py:1709-1717 and raises
`ReviewedEntryError` only afterwards (vault.py:1739-1744). After the import, the entry is unchanged and
keeps its attestations, but the hash-chained journal holds an `attestations_reset` event for it. The
journal records a security-relevant event that did not happen, and `verify_audit_chain` passes. The
same mechanism applies to every statement `_put` runs before a later refusal (for example
`_cascade_invalidate` or a supersession). This is the same in-transaction ordering problem as R1-1,
seen from the SQLite side.

### R1-4 (medium) — MCP forget's erasure is not resumable after a kill

Repro: `tests/review1_forget_scrub_not_resumed.py` (1 failed, 1 passed; real SIGKILL in a child).

`KibisisMCPServer._forget` (mcp_server.py:587-608) commits `tombstone()` (its own transaction,
_vault_tombstone.py:308-351/353+) and then calls `scrub()` (_vault_tombstone.py:627-644: FTS rebuild,
commit, checkpoint, VACUUM). SECURITY.md:20 and :387-388 say the words of deleted entries stay in index
pages and free pages until `scrub()`, and that the MCP forget runs it. If the process dies between the
two, nothing records that a scrub is owed: `__init__`, `close()` and later writes never scrub. After a
SIGKILL at that point, a fresh open, a later write and a close, the forgotten text is still in the
file (2 copies in a plaintext vault: the FTS segment and free pages). The uninterrupted forget removes
it (control).

Scope: in a SQLCipher vault the leftover bytes are under whole-file encryption, so this matters for
plaintext vaults and for anyone holding the passphrase. FTS also indexes `category` and `key` in
plaintext for keyed non-SQLCipher vaults (vault.py:1059-1078), so a forgotten key survives the same
way. That case is not separately tested.

### R1-5 (medium) — AML Add is acknowledged as durable under synchronous=NORMAL

Repro: `tests/review1_aml_ack_not_durable.py` (1 failed, 1 passed).

aml_adapter.py:16-17 says "`success` is returned after commit, when the messages are durable".
`_configure_db` (vault.py:961-965) sets `journal_mode = WAL` and `synchronous = NORMAL` on every
vault, and nothing under src/kibisis calls fsync on the database. With WAL and NORMAL, SQLite does not
sync the WAL at COMMIT, so an acknowledged Add can roll back after an OS crash or power loss. The
benchmark then believes it stored messages that are gone, and a retry with the same `request_id` is
no longer recognised as a retry. The control shows that durability against a process kill holds: a
fresh open sees the committed request. The test proves the setting, not a simulated power cut, which
cannot be reproduced in-process. The same caveat applies to every "reported durable" vault write. The
claim is only explicit in the AML adapter.

### R1-6 (low) — killed OKF export leaves an ungated plaintext staging bundle forever

Repro: `tests/review1_okf_stage_leak.py` (1 failed, 1 passed; real SIGKILL in a child).

`export_bundle` writes every rendered document into `.okf-stage-XXXX` beside the output
(okf/export.py:653-677, 824), runs `bundle_gate` on it (okf/export.py:826-827; `command_gate` allows
900 s), and only then swaps it in (okf/export.py:680-698). The stage is removed only by
`except BaseException` (okf/export.py:843-845) or, after a successful exchange, by the rmtree at
okf/export.py:689. A killed process runs neither. `_prepare_out` (okf/export.py:587) and later
exports never sweep stale `.okf-stage-*` / `.okf-old-*` directories. After a kill during the gate, and
then a successful export, the killed run's full bundle, which the gate was still judging, remains
next to the output. It is mode 0700, and it holds decrypted vault content under a hidden name. A kill
between the exchange (okf/export.py:688) and the rmtree (okf/export.py:689) leaves the previous
bundle there in the same way. That case is not separately tested.

### R1-7 (low) — key file is created at its final path before the key is written

Repro: `tests/review1_keyfile_partial.py` (1 failed, 1 passed).

`generate_keyfile` (keys.py:34-38) creates the final path with `O_CREAT|O_EXCL` and then writes the
key. There is no temp name, rename, cleanup or fsync. A kill between the two steps leaves an empty
file. `main` then refuses to replace it ("already exists; not overwriting it", keys.py:53-55), and
`resolve_passphrase` reads the empty file as "no passphrase" (keys.py:28-30, `... or None`), so
`open_vault` behaves as if no key was configured. No vault data is lost, because the key was never
used, but the operator gets a misleading state. Without an fsync, a power loss after a vault was keyed
with a fresh key file can leave that file empty (not tested; not modelable in-process).

## Checked and not defective under this cut (no file)

- `_write_tx` (vault.py:888-913): BEGIN IMMEDIATE, rollback on BaseException, single commit. The
  journal row, `audit_head` and the high-water mark (_vault_audit.py:193-290) commit together with the
  change.
- Plain to SQLCipher conversion (vault.py:520-557, 594-610, 916-950): the plain file is untouched
  until `os.replace`. A stale `<path>.tmp_enc` is removed by the next attempt (vault.py:928-930). The
  temp WAL is TRUNCATE-checkpointed before adoption.
- Kills inside `_upgrade_to_format_3`, `_persist_verification_quorum` and `_ensure_search_index` on a
  fresh vault: the file reopened (scratch probe). Only the window in R1-2 bricks the file.
- Snapshot export to a file (_vault_snapshot.py:155-172): O_EXCL temp file, 0600, fsync, then
  os.replace. A kill leaves a `.tmp.<pid>` file (0600, decrypted). It is not swept, but it is pid-named
  and owner-only. Not filed.
- AML Add (aml_adapter.py:515-520): one outer `_write_tx`. `put_batch`'s `with self._conn:` commits at
  its end, so the request and its marker land together.
- `review_entity` (_vault_review.py:408-453): the tombstone, the transition and the cascade run inside
  the caller's single write transaction (apart from the Argus mirror, R1-1).

## Not verified

- Lease coordinator: native Rust (`kibisis_native`, lease.py). Its syscalls cannot be interrupted
  in-process from Python, and building the crate is out of bounds.
- Power-loss or OS-crash ordering: no fsync of directories after any rename (okf/export.py,
  _vault_snapshot.py:168), and the file and WAL durability under synchronous=NORMAL. Argued, not
  simulated, except for the setting check in R1-5.
- Integrity upgrades of older on-disk formats (a5 / format 1 / format 2 files), which commit in
  several transactions (_vault_crypto.py:1117, then `_upgrade_to_format_3`). There was no fixture for
  an old-format file in this round.
- OKF import (okf/importer.py:405-494): each file is its own `put`. It is not atomic across a bundle by
  design, and resumability was not tested.
