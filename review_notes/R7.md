## Findings

### R7-4 — Medium — journal wipe with the head left intact is caught only until the next append
*Where:* `_vault_audit.py` `_append` (reads `SELECT sequence, event_hash FROM audit_journal ORDER BY sequence DESC
LIMIT 1`, never the signed `audit_head`), `_write_audit_head` (INSERT OR REPLACE).
*Problem:* a file writer runs `DELETE FROM audit_journal` (or `DROP TABLE audit_journal`, or deletes rows *and*
head). `verify_audit_chain()` correctly reports "a signed head with no rows: the whole journal was removed"
(or "no signed head") at that moment. The very next append — any routine agent write through MCP `remember` —
starts a fresh chain at sequence 1 / prev `0*64` and overwrites the signed head over the one-row chain.
`verify_audit_chain()` is True from then on, on every reopen; the only trace is that `list_audit_events()`
starts at 1 with a recent timestamp. `journal_anchored` records only "has held a row", not a high-water
sequence, so nothing durable contradicts the new chain. In the threat model the file writer is in scope and
the agent writes routinely, so the detection window is one write.
*Repro:* `test_attack_r7_emptied_journal_with_head_intact_is_laundered_by_the_next_write` (all three variants).
*Docs:* SECURITY.md:69 "deleting every row together with the head is caught too" and :178-180 — true only
until the next append; the branch replaced the tag's test `test_deleting_journal_and_head_together_is_not_caught`
with `..._is_caught`, which asserts the momentary state only.
*Fix (not applied):* in `_append`, read `audit_head` first and refuse (or journal a `journal_truncated` event
with the old head sequence/hash and keep it under the MAC) when the table's last row does not match the signed
head; or bind the head's sequence into `vault_meta` as a monotonic high-water mark under the meta MAC and verify
`last_sequence >= high_water`. Either way, re-add the assertion that the chain is still False *after* a write.

### R7-1 — Low — adopted rows stay plaintext (and FTS-indexed in the clear) inside the now-keyed vault
*Where:* `_vault_crypto.py` ~1188 `_write_sealed(cursor, r, content, encrypt=r["is_encrypted"] == 1)`; every
keyless row has `is_encrypted = 0`.
*Problem:* with the opt-in the rows are MAC-bound and demoted, but not sealed: `entities.content` keeps the
plaintext, `entities_fts` keeps the words, `encryption_status()` reports `{'encrypted': 0, 'plaintext': 3}`.
A model `_put` in the same vault seals (`is_encrypted=1`, content ``). Only the library-only
`migrate_plaintext()` seals them; no CLI/MCP path calls it. In SQLCipher mode the file is encrypted anyway;
in the no-SQLCipher mode (the one the tests run) the "passphrase" vault carries the adopted text in the clear
indefinitely. The content was plaintext before adoption, so this is a confidentiality *expectation* gap, not a
new exposure.
*Repro:* `test_attack_r7_adopted_content_stays_plain_on_disk_until_migrate_plaintext`.
*Docs:* SECURITY.md:128 "stored exactly as a model-origin `put` stores an agent's write" (overstated: the
column `is_encrypted` differs); SECURITY.md "Without SQLCipher" table row "Passphrase, no SQLCipher | Sealed
(AES-GCM)" (understated: adopted and legacy-plain rows are not). `health` does show `plaintext_entries`.
*Fix:* seal adopted rows in the adoption transaction (`encrypt=True` when `not was_keyed`), or have the
adoption report and the CLI notice say "N entries still plaintext; run migrate_plaintext".

### R7-3 — Low — a `verification_quorum` planted in a salt-less file is taken as the vault's policy
*Where:* `vault.py` ~1320 (quorum check), `_vault_crypto.py` adoption transaction (meta MAC re-sign).
*Problem:* the keyless file is "on nobody's word" for rows, journal and every other meta key (R6-1b drops
non-init keys from the gate's point of view), but `verification_quorum` is read as the stored policy:
(a) planted `7` (> default) is adopted and MAC-signed by the opt-in open with no notice; every plain open
afterwards is refused with ConfigError until the operator sets the env to 7, and a pinning open "that asks
for less is refused" (SECURITY.md:249), so the lock-out needs manual meta surgery — a DoS a file writer can
get more cheaply by deleting the file, hence Low. (b) planted `1` (< default): the opt-in open raises
ConfigError — **after** the adoption transaction has committed (salt, key check, MAC, demoted rows, chained
journal). The "refused" open therefore converted the file and MAC-signed the planted 1 as the stored quorum;
the error's remedy is "Set KIBISIS_VERIFICATION_QUORUM=1", and an open that follows it needs no opt-in and
runs at quorum 1. The operator still has to choose 1 explicitly, so this is Low, not Medium.
*Repro:* `test_attack_r7_planted_high_quorum_in_keyless_file_is_adopted_and_signed_silently`,
`test_attack_r7_planted_low_quorum_refusal_has_already_committed_the_adoption`.
*Fix:* drop `verification_quorum` (and `quorum_dropped_from`) from a salt-less file during adoption exactly as
the legacy-MAC path does, log at WARNING with the value, and run the quorum check before the adoption commit.

### R7-2 — Minor — `kibisis-review list` refusal names a flag `list` does not accept
*Where:* `review.py` `_parser` (`_add_adopt_keyless` only on verdicts and `lift`), refusal text from
`_refuse_unadopted_keyless_rows`.
*Problem:* `review list` on a keyless file exits 2 with "pass --adopt-keyless to adopt them as candidates";
`review list --adopt-keyless` is "unrecognized arguments". The design (SECURITY.md:123) is deliberate — only
terminal-gated commands adopt — but the message should say so. The `_adoption_line` branch "in memory only:
this read-only open wrote nothing" is reachable only from the library (`read_only=True, adopt_keyless=True`),
never from a CLI.
*Repro:* `test_attack_r7_review_list_refusal_names_a_flag_list_does_not_accept`.

## Release verdict

In my judgement the branch is ready to merge to `main` as the alpha.17 candidate **with R7-4 filed as a known
issue and SECURITY.md:69/:178 corrected to "caught until the next append" before the tag**; it is not a
regression against alpha.16 (the tag documented the same wipe as *not caught* at all), every R2–R6 finding is
verifiably closed by collected tests, the whole-branch sweep found no deleted or weakened assertion, and the
default suite is green (1270 passed, 5 skipped). The three residual limits an operator must know: (1) a file
writer who empties the journal is detected only until the next agent write — keep the head sequence/hash (or
the Argus ledger) outside the file if journal continuity matters; (2) the keyless-adoption door is operator
opt-in only and yields agent-class candidates, but it does not seal the adopted text (run `migrate_plaintext()`
in the no-SQLCipher mode) and it imports a planted `verification_quorum` as vault policy; (3) the terminal gate
on `admit`/`review` stops pipes and cron, not an agent that can allocate a pty in the operator's account, and
the same-uid shell can run the review CLI — SECURITY.md says both, and alpha.17 should keep saying both.
