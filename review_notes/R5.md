## Findings (most severe first)

### R5-1 — the discriminator guards one door; the salt-absent door re-enters the migration as a "never-keyed vault" and adopts, seals and signs whatever the file writer wrote — **high** (file writer; same cost as R2-B1/R3-AB2/R4-1: the sealed text is lost; stronger outcome: rows adopted as `verified`, not left unsigned)
*Where:* `_vault_crypto.py:454` (`_refuse_unless_genuine_a5`: `if meta.get("kdf_salt") is None ...: return None`,
"not a candidate"); `vault.py:491-501` (`_was_keyed = _has_meta_key("kdf_salt")` is False, `_vault_salt()`
issues a fresh salt because `_refuse_keyed_records_without_salt` (`:171-192`) only fires when a key check,
MAC or format ≥ 2 is *left*); `_vault_crypto.py:575-585` (the "must have been checked as a5" guard is
behind `elif self._was_keyed`); `:845-868` (`_migrate_integrity`: `was_keyed = self._was_keyed or any(is_encrypted == 1)`
is False → every row goes to `entries_adopted_from_keyless_vault`, signature not consulted); `:917-919` (the
chain is also tried under the path-derived key when `not self._was_keyed`).
*Problem:* R2-B1 → R3-AB2 → R4-1 all kept `kdf_salt` and were closed by witnesses on the salt-present path.
Deleting **all** of `vault_meta` (salt included) and setting every row `is_encrypted = 0, envelope = NULL,
tenant_sig = NULL, content = <anything>, epistemic_state = 'verified'`, dropping tombstones and re-chaining the
journal headless in format 1 makes the file one that "never had a passphrase". The next writable open with
the real passphrase runs no discriminator, writes a fresh salt, migrates with
`entries_adopted_from_keyless_vault: 3, entries_resealed: 3, entries_left_unsigned: 0`, seals and signs the
forged rows under the real key with the writer's epistemic state, writes key check and MAC,
`verify_audit_chain()` is True, `is_tombstoned(VALUE)` is False and `remember(VALUE)` is accepted; the
read-only open shows the same. A read-only open *before* the writable one reads the file "as the plaintext
vault it is" (`vault.py:737-742`) and already returns the forged content. Inside the file nothing tells it from
a vault the current code wrote without a passphrase (`vault_meta` empty, a head row, format 3 events, rows
signed under the path key — all computable from the path; the laundered file passes without even those).
SECURITY.md:144-146 admits the salt removal "looks like it never had a passphrase … told apart from a new
vault only by a copy of the head"; but the docstring (`_vault_crypto.py:443-445`) and SECURITY.md:102-106 say
the only reset the discriminator cannot tell is "an empty vault … not a vault whose rejections were
laundered" — this one is not empty and its rejections are laundered.
*Repro:* `review5_discriminator.py::test_attack_r5_1_salt_absent_reset_launders_a_keyed_vault_as_never_keyed`
(passes). `::test_control_a_genuine_never_keyed_vault_and_the_laundered_file_differ_only_by_what_the_writer_chooses`
shows the genuine keyless shape.
*Fix:* the keyless→keyed adoption is the only place where plaintext rows become signed `verified` entries
without a person's act. Options, strongest first: (1) never adopt silently — a first keyed open of a file with
rows requires an explicit opt-in (`adopt_keyless=True` / a CLI flag behind `require_terminal`), otherwise
refuse with "this file has N plaintext entries and no salt; a keyed vault whose records were removed looks the
same"; (2) adopt but demote: every adopted row becomes `candidate` with attestations reset, and the `migrate`
event (which today is written) is surfaced by `health`/`review list` as "N entries adopted from a keyless
file on <date>"; (3) at minimum, have the discriminator docstring and SECURITY.md:102-106 say that the
salt-absent reset is a second, un-discriminated door with this outcome, and move the sentence at :144-146
next to it.

### R5-2 — the admitted "empty vault" reset is empty of entries only: planted tombstones get MAC-signed and planted audit history gets chained into the signed head — **low–medium** (file writer; needs the full reset; gives the writer signed tombstones and a signed forged journal)
*Where:* `_vault_crypto.py:528-541` (the empty-table witness counts only `put`/`update` events);
`:892-908` (every tombstone row found is re-keyed and given a `tombstone_mac`); `:933-948` (every event is
re-chained under the real key).
*Problem:* on top of the schema scrub + rows deleted + entry events deleted, the writer inserts tombstone rows
with plain SHA-256 digests (any class, any scope) and journal rows of any non-entry action under any author
(`tombstone`, `attestations_reset`, `state_transition`, …), re-chained headless. The discriminator finds no
witness; the migration keys and signs the tombstones (`tombstones_rekeyed: 1`) and signs the history:
`verify_audit_chain()` True in both open modes, the planted value is rejected in the operator's scope with a
valid MAC (`remember` raises `TombstonedValueError`; a signed tombstone is otherwise unobtainable without the
key), and the forged events read as authentic. Not laundering a rejection, but the mirror image: the writer
mints rejections and audit history the vault then vouches for.
*Repro:* `::test_attack_r5_2_the_empty_vault_reset_signs_planted_tombstones_and_audit_history` (passes).
*Fix:* "an empty vault" should mean empty: with no entity row, refuse the migration when the tombstone table
or the journal is non-empty (an a5 file with no entries and a journal has nothing to lose), or make the
empty-table witness count *any* row/event rather than `put`/`update` only. Also say in SECURITY.md:102-106
what the admitted state may still carry.

### R5-3 — sealed rows with no `vault_meta` at all get a fresh salt and the schema upgrade written before the wrong-passphrase refusal — **low** (file writer; the refusal has written; the file's second refusal is a different error)
*Where:* `vault.py:482-492` (`_init_schema` then `_vault_salt()` before `_upgrade_integrity`);
`_vault_crypto.py:176-178` (no keyed record left → "never keyed" → a salt is issued); `:885-886`.
*Problem:* `DELETE FROM vault_meta` (or `DROP TABLE vault_meta`) with the rows still sealed: the discriminator
is not a candidate, a fresh `kdf_salt` is committed, then every row fails to open and the open raises
"Failed to authenticate … passphrase". The refused open changed the file (new salt, `audit_head`, `format`,
`tombstone_mac`); the next open with the right passphrase is refused as "not a 0.1.0a5 file … audit_head …
3 of 3 entries sealed with its binding", a different story than the first. SECURITY.md:108-110 ("no fresh salt
is written over it") holds only while a key check, MAC or format record remains. A sealed row (`is_encrypted = 1`)
is itself proof the file was keyed; it should block the fresh salt the way the records do.
*Repro:* `::test_attack_r5_3_sealed_rows_without_any_vault_meta_get_a_fresh_salt_before_the_wrong_passphrase_refusal` (passes).
*Fix:* in `_refuse_keyed_records_without_salt`, also refuse when any entity row has `is_encrypted = 1` (and,
for R5-1, treat that as a keyed-records witness too); run it before `_init_schema`.

### R5-4 — after a legacy-MAC restore the dropped quorum is re-pinned by the next pinning open at whatever that process runs with — **low** (residual of the R4-2 design; needs a pre-quorum copy of the file and a later verdict run without the person's env)
*Where:* `vault.py:1199-1204` (`_persist_verification_quorum`: `stored is None` + `pin_quorum` → store the
process's quorum, the default unless named); `_vault_crypto.py:650-653` (the drop).
*Problem:* a person pinned 3 (env set for that run). The file writer restores `meta_mac` from a pre-R2-B4 copy
(the V1-bound values have not changed, so it verifies over the legacy set; without such a copy no edit makes a
full-set MAC legacy — control below). The next writable open drops the 3 with a WARNING; the person's next
verdict, run without `KIBISIS_VERIFICATION_QUORUM`, pins 2 silently and permanently (a later env-3 open raises
it again, but `verified` was mintable on two accounts in between). The end state is R4-2's, one step later;
the WARNING at the drop names the value and the env to re-pin, which is the mitigation.
*Repro:* `::test_attack_r5_4_after_a_legacy_mac_restore_a_verdict_run_without_the_env_pins_the_default` (passes).
*Fix:* after a drop, record `quorum_dropped_from = 3` (under the full-set MAC) and refuse a pinning open that
would pin below it unless it names its quorum — or simply refuse to re-sign a legacy MAC until a pinning open
names a quorum.

## Discriminator claim
Verdict on "the only reset that passes is a headless journal + no entry event + no sealed entry = an empty
vault": **true for the salt-present class it examines, and that class is not the whole migration entry.**
Furthest state on the salt-present path: the schema scrub + rows deleted + entry events deleted *plus* planted
tombstone rows and non-entry journal events (R5-2) — admitted, signed. Furthest state overall: the same reset
with `vault_meta` deleted *including the salt* and forged plaintext rows (R5-1) — admitted, rows adopted as
signed `verified`, rejection laundered; the discriminator returns None at line 454 before looking at anything.
The admitted empty reset writes no `migrate` event (`_migrate_integrity:840-843`), so it is also
indistinguishable from a vault created fresh (`::test_control_the_empty_reset_leaves_no_migrate_event_so_it_reads_exactly_as_a_new_vault`).
