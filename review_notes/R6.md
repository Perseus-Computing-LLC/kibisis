## Findings (most severe first)

### R6-1 — the second door is guarded by row count only: a salt-less file with **no rows** and a planted journal is chained under the signed head by any keyed open (MCP/AML/OKF, no opt-in, nothing surfaced) — **low–medium** (file writer; the keyless mirror of R5-2; gives the writer a signed forged audit history and, by extension, "an empty vault" that any server silently keys)
*Where:* `_vault_crypto.py:235-258` (`_refuse_unadopted_keyless_rows` looks at `entities` and
`rejected_value_tombstones` only; `_keyless_rows:226`); `:986` (`if not (rows or tombstones or events)` →
with events present the empty branch is skipped); `:1008` (the adopt refusal needs `rows`); `:1088-1091`
(the chain is tried under the path-derived key when `not self._was_keyed` — the key a file writer computes);
`:1101-1115` (every event re-chained under the real key); `:341-357`/`keyless_adoption` (reports
`entries_adopted_from_keyless_vault > 0` only, so 0 rows = nothing shown).
*Problem:* R5-1's file with `DELETE FROM entities` on top, plus any journal the writer likes
(`put`/`state_transition`/`human_review`/`attestations_reset` on a ghost entry, author `alice`, metadata
`{"verdict": "verified", ...}`), re-chained headless in format 1. `config.open_vault(path)` — the MCP
server's open, the AML pool's `_open`, `_open_okf_vault`, `review list` — passes both pre-`_init_schema`
refusals (0 rows, 0 tombstones), migrates with `entries_adopted_from_keyless_vault: 0`, re-chains the four
planted events under the passphrase key, writes `audit_head`, key check, MAC and a `migrate` event;
`verify_audit_chain()` is True writable and read-only afterwards; `keyless_adoption()` is None, so
`health` and `review list` say nothing. R5-2 closed exactly this on the salt-present door ("an empty vault
means empty: no tombstone row and no journal event"); the salt-absent door inherited the old rule.
A variant: `DROP TABLE entities` — read-only says "not a kibisis vault (no entities table)", the writable
keyed open re-creates the table and signs the planted journal the same way (`vault.py:727` vs `:491`).
*Repro:* `::test_attack_r6_1_keyless_file_with_no_rows_and_a_planted_journal_is_signed_without_the_opt_in`,
`::test_attack_r6_1b_a_keyless_file_without_an_entities_table_is_rebuilt_writable_and_its_journal_signed` (both pass).
*Fix:* in `_refuse_unadopted_keyless_rows`, count journal events too (`audit_journal` non-empty with no
salt → refuse without the opt-in, exactly as rows do; with the opt-in, say so in the `migrate` event and
make `keyless_adoption()` report `events_adopted` as well); or, in `_migrate_integrity`, never chain a
format 1 journal that only verifies under the path key without the opt-in. Make the writable open
refuse a file without an `entities` table the way the read-only open does.

### R6-2 — demotion is incomplete: adopted candidates keep the reserved K-R1/K-R2 keys (`origin_class`, `act_class`, `author_id`, `superseded_by`, `supersedes`, `proposed_supersedes`), so a forged principal-class candidate blocks the agent's writes like a tombstone and rides a single verdict into a verified principal `act` entry — **medium** (file writer + a person's `--adopt-keyless`; the opt-in is documented as yielding "candidates … as a model-origin write would be stored", which is not what it yields)
*Where:* `_vault_crypto.py:336-339` (`_TRUST_METADATA_KEYS` = `human_reviews, attestations,
verification_pending, act_class_capped_from, trust_inherited_from, last_verified_at`); `:341-357`
(`_demote_adopted_row`: "The origin and origin class stay as stored"); `vault.py:111-116`
(`RESERVED_METADATA_KEYS`: `origin_class`, `act_class` are "set by the vault from the write path, never
from the payload"); `:125` (`PRINCIPAL_METADATA_KEYS`: `author_id`, `supersession`, `proposed_supersedes`,
`slot` — only a principal write may set them); `:1568-1578` (K-R1: a lower-class write on a
principal-class row raises `OriginClassError`); `:1521-1526` (K-R2: a row with `superseded_by` refuses
every non-principal write); `_vault_review.py:44-53` (`_row_origin_class` trusts the stored
`origin_class`).
*Problem:* a model-origin write is stored with `origin_class: agent`, `act_class: inform`, no top-level
`author_id`. The adopted row keeps whatever the writer put there. With `origin_class: principal` on the
forged row (origin `model`), the agent's `remember("decision", "k0", …, origin="model")` raises
`OriginClassError` — the key is locked from below with no tombstone (the very outcome the tombstone
refusal in `_refuse_unadopted_keyless_rows` exists to prevent); with `superseded_by` set on the row,
`SupersededEntryError`. And when the person then approves the candidate (one verdict at quorum 1),
the result is `verified`, `origin_class: principal`, `act_class: act` — an action-driving,
principal-class entry nobody established; the reviewer saw content, not metadata. `author_id: alice` is
also kept and shown as the author in recall. (`human_reviews` is dropped and a later verdict records
the reviewer's account, not the row's author: control below.)
*Repro:* `::test_attack_r6_2_adopted_candidates_keep_forged_origin_class_act_class_and_block_agent_writes`,
`::test_attack_r6_2b_a_persons_approve_of_the_adopted_candidate_yields_a_verified_principal_act_entry` (pass);
`::test_control_adopted_rows_cannot_mint_a_review_from_their_author_id` (passes: author_id does not mint).
*Fix:* `_demote_adopted_row` should re-derive the row as a model-origin write would be stored: set
`origin_class` from `origin_class_of(origin)` capped at `agent` (or always `agent`), `act_class = inform`,
drop `author_id`/`supersession`/`proposed_supersedes`/`slot` (move them under `agent_metadata` the way
`_put` does for a non-principal write), and clear the `superseded_by`/`supersedes` columns. Document
that `origin` is kept as a label only.

### R6-3 — read-only open with the opt-in serves the forged rows undemoted, state `verified`, with no adoption notice — **low** (programmatic path only: `review list` and the servers never pass the opt-in; contradicts SECURITY.md:169 "the writer's rows are never served as verified")
*Where:* `vault.py:727-735` (read-only: `_refuse_unadopted_keyless_rows` then "served as the plaintext
vault it is"); `_demote_adopted_row` runs only in `_migrate_integrity` (writable).
*Problem:* `SQLiteMemoryVault(p, passphrase=…, read_only=True, adopt_keyless=True).list_entities()`
returns every forged row with `epistemic_state = verified` and `content = FORGED …`;
`keyless_adoption()` is None. The constructor docstring says the opt-in makes "every adopted entry a
candidate … read-only or writable". No CLI reaches it (`review list` opens read-only without the kwarg
and is refused: control), so this is a library-API/doc gap, and the only R5-1 outcome where a forged
`verified` state is served under a passphrase.
*Repro:* `::test_attack_r6_3_read_only_open_with_opt_in_serves_the_forged_rows_undemoted_as_verified` (passes);
`::test_control_read_only_open_with_opt_in_writes_nothing` (bytes/mtime unchanged).
*Fix:* in read-only mode with the opt-in, serve every row as `candidate` with the trust keys masked
(apply `_demote_adopted_row`'s view in `_open_entry`/listing), or refuse `adopt_keyless` read-only
("adoption needs a writable open") and say so in the docstring.

### R6-4 — under a legacy MAC a planted `quorum_dropped_from` (or a planted `verification_quorum` that becomes the floor) is re-signed and blocks every unnamed verdict until the person names a quorum — **low** (file writer with a pre-quorum copy of the MAC; a value nobody signed becomes signed, but as a floor, never as a quorum; cleared by any named quorum)
*Where:* `vault.py:1195-1215` (`_drop_untrusted_stored_quorum`: `floor = max(dropped,
self._dropped_quorum() or 0)` reads the unsigned record; and when no `verification_quorum` is stored the
method returns early and `_write_meta_mac` signs the planted record as-is, since `_meta_mac_fields`
includes `VAULT_META_BOUND_OPTIONAL`); `:1238`, `:1258-1266` (pinning open naming no quorum → `ConfigError`).
*Problem:* a never-pinned vault with its V1 MAC restored plus `INSERT INTO vault_meta
('quorum_dropped_from', '99')`: the next writable open (a server's) accepts the legacy MAC, re-signs
over the full set with the planted 99, `quorum_dropped_from == 99` under a MAC that now refuses edits;
every `kibisis-review <verdict>` / admit without `KIBISIS_VERIFICATION_QUORUM` is refused "pinned at 99".
The person clears it by naming any quorum (`_quorum_requested`), so it is a nuisance and a misleading
message ("had its verification quorum pinned at 99" — it never was), not a lowering. R4-2's rule "no
path re-signs a value that was not under the MAC" now has one exception by design (the floor); this is
that exception fed from the file.
*Repro:* `::test_attack_r6_4_a_planted_quorum_dropped_from_under_a_legacy_mac_is_signed_and_blocks_unnamed_verdicts` (passes);
`::test_control_quorum_dropped_from_cannot_be_edited_or_deleted_under_a_full_set_mac` (full-set MAC holds).
*Fix:* in the legacy re-sign, delete any pre-existing `quorum_dropped_from` (it was not under the MAC)
before computing the floor from the dropped `verification_quorum` alone; cap the floor at the dropped
value; word the refusal as "a stored quorum of N was dropped" rather than "pinned at N".
