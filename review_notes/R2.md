# R2 — atomicity and crash consistency (round 2: the round-1 fix and what it left)

Cut: what state a fresh open can see after a kill between any two syscalls of a write path.
Head: `021e60c4ce14` (detached). Round-1 fix diff: `git diff 74129f5 021e60c -- src SECURITY.md CHANGELOG.md`.
Every finding below has a repro `tests/review2_*.py` that exits 1 on this head when run alone. In each file
`test_control_*` asserts behaviour that holds (passes; proves the fixture), `test_attack_*` asserts the
correct post-crash behaviour and FAILS because of the defect.

How a crash is modelled: a monkeypatched step between two syscalls raises a `BaseException` subclass
(`_Killed`) standing in for the process dying there. Where the code's own `except`/`finally` cleanup would
run and a SIGKILL would not, that cleanup is made a no-op for the killed call and the test says so. A fresh
object then reopens from disk. Dead pids come from a finished child process.

## Findings

### R2-1 (high): a failed resumed scrub leaves the open's connection inside a transaction, and every later write is lost at close

Round 1 added `_resume_owed_scrub` (`src/kibisis/_vault_tombstone.py:658-670`), which runs at the end of
every writable open (`src/kibisis/vault.py:566-569`). `scrub()` starts with
`self._conn.execute("INSERT INTO entities_fts(entities_fts) VALUES ('rebuild')")` (`_vault_tombstone.py:690`),
which runs outside `_write_tx`, so the driver opens an implicit transaction first. When that statement fails,
for example with `database is locked` because another process held the write lock past the 30 s busy
timeout (`vault.py:574`), or with a full disk during the rebuild, the `except Exception` at
`_vault_tombstone.py:669-670` logs "retried at the next open" and returns. Nothing rolls back.

The vault object is handed out with `_conn.in_transaction == True`. From then on `_write_tx`
(`vault.py:920-934`) treats every write as nested: it opens a SAVEPOINT and RELEASEs it, and nothing ever
commits. `put` returns, `get` on the same object reads the row back, and the AML adapter acks the Add. All
of it is discarded at `close()`. Argus records queued in that window are never flushed, and once the
connection has written it holds the write lock, which blocks every other process until it closes.

The trigger is a kill-before-scrub (round 1's own window) combined with lock contention at the next open.
This is the round-1 fix's new window.

Proof: a child process holds `BEGIN IMMEDIATE` while the vault is reopened. The busy timeout is cut to 0.3 s
through the vault's own `sqlcipher3.connect` call. The attack test sees the put reported done and visible
to its writer, but absent after reopen (`in_transaction` was True). The control test shows the same resumed
scrub succeeding without contention, and the write is durable.

### R2-2 (medium): one scrub clears the debt of an erasure committed while it ran

The scrub debt is a single row, `pending_scrub` id=1 (`_owe_scrub`, `_vault_tombstone.py:641-647`), with no
generation or high-water mark. `scrub()` rebuilds the FTS, then runs VACUUM and a checkpoint
(`:690-698`), and then, in a separate transaction, runs `DELETE FROM pending_scrub` unconditionally
(`:699-701`). Suppose a tombstone from another connection commits after that VACUUM and before the DELETE.
Its debt is cleared even though none of its bytes were scrubbed. If that process is then killed before its
own `scrub()`, which is exactly the window round 1's debt exists for, the next open finds no debt and the
deleted plaintext stays in the file. Multiple processes on one vault are expected: MCP server, AML adapter,
CLI.

Proof: A's `scrub_owed` check is interleaved with B's `tombstone`, then B is killed before its scrub. A
fresh open reports `scrub_owed() == False` and the token is still in the file. The control runs the same
sequence with B's tombstone after A's scrub has finished, and the debt is paid at the next open.

### R2-3 (medium): the OKF leftover sweep matches set-aside bundles by name suffix and destroys another output's only copy

`_swap_into_place`'s fallback (`src/kibisis/okf/export.py:775-781`) renames the previous bundle to
`.okf-old-<pid>-<hex>.<out.name>` and then renames the stage into `out`. A kill between the two renames
leaves `out` missing, and its previous bundle exists only under the set-aside name. That previous bundle
includes `log.md`, which carries every earlier export's history forward and cannot be regenerated.

The round-1 `_sweep_stale_leftovers` (`:693-733`, called at `:863` for every export into the same parent)
decides ownership with `name.endswith("." + out.name)` (`:720`, `:727`). `.okf-old-N-<hex>.shared.bundle`
ends with `.bundle`, so an export to `bundle` claims it. If `bundle` exists, the leftover is `rmtree`d
(`:733`). If `bundle` is missing, the leftover is renamed into it (`:729`) and then replaced. Either way
`shared.bundle`'s only copy is gone. Severity is medium rather than high because the vault content survives
and can be re-exported. The export history in `log.md` is lost.

Proof: after a kill between the two renames, exporting to `bundle` leaves `['bundle']`, and both
`shared.bundle` and its set-aside copy are gone. The control uses `shared_bundle`, where no suffix collides,
and restores correctly with the history kept.

### R2-4 (medium): `export_snapshot(path=...)` temp file is never swept; plaintext leaks and later exports from the same pid fail

This write path was not touched by round 1. `export_snapshot` (`src/kibisis/_vault_snapshot.py:155-172`)
writes the decrypted snapshot to `out.with_suffix(".tmp.<pid>")` using `O_CREAT|O_EXCL` (`:158-162`). Only
its own `except` handler unlinks the temp (`:169-171`), and a SIGKILL never runs that handler. Nothing
sweeps the file. A kill between the write and `os.replace` (`:168`) has two consequences:

- The vault's decrypted content stays beside the snapshot regardless of later exports. SQLCipher protects
  the vault file, not this one.
- Every later export to the same path from the same pid raises `FileExistsError`. A container entrypoint is
  pid 1 on every run, so scheduled snapshots stop for good.

Round 1 fixed exactly this class of leftover for OKF export and key files (R1-6, R1-7) but not here.

Proof: the kill is modelled at the temp's `os.fsync`. The first attack test (same pid) gets `FileExistsError`.
In the second attack test the leftover is renamed to a dead pid, and it still holds the plaintext after a
successful export.

### R2-5 (low): the OKF stage sweep trusts a bare pid, so a container (pid 1) or a reused pid keeps the ungated stage forever

`_is_stale` (`okf/export.py:684-690`) treats a stage as live if its pid equals `os.getpid()` or is alive.
Stage files are rendered before any bundle gate runs (`_write_stage`, `:736-760`) and contain ungated
plaintext. A run that is killed as pid 1 in a container, where the next run is also pid 1, or whose pid was
reused, leaves that stage beside the bundle permanently. This is the R1-7 leak that round 1 meant to close.

Proof: a real export is killed inside its bundle gate, with its `rmtree` cleanup disabled as a SIGKILL
would skip it. With a dead-pid name the next export removes the stage (control). With the pid-1 name the
stage survives (attack). Severity is low because it needs pid reuse or a containerised exporter, and the
directory is 0700.

### R2-6 (low): a kill between `os.link` and the temp unlink leaves a permanent hidden copy of the installed key

`generate_keyfile` (`src/kibisis/keys.py:91-127`) has this order: write and fsync the temp (`:111`),
`os.link(temp, path)` (`:113`), `_fsync_dir` (`:122`), then `os.unlink(temp)` in `finally` (`:123-125`). The
docstring and `_sweep_stale_temps` (`:58-78`) assume a leftover temp is never-installed key material. After
a kill post-link, the temp is a second name for the installed key. Every later run returns at
`os.path.lexists(path)` (`:100`) before the sweep (`:104`), so the copy is never removed. Retiring the key by
deleting `path` leaves the key on disk.

Proof: a kill at the temp unlink, with the temp's pid made dead. The next `keys.main([path])` returns 1, and
`.kibisis.key.tmp-<pid>-<hex>` still holds the key.

### R2-7 (low): OKF export publishes and deletes the previous bundle without fsyncing anything

`_write_stage` writes each document with no `os.fsync` (`okf/export.py:754-757`). `_swap_into_place`
(`:763-781`) exchanges or renames the stage into place and then `rmtree`s the previous bundle, and no
directory is fsynced. After an OS crash or power loss, `out` can name a bundle of empty files while the
previous bundle (and its `log.md` history) is already deleted. Round 1 made key files and vault commits
durable, but not this temp-and-rename.

Proof: `os.fsync` calls are recorded during export. At the swap, `default/decision/alpha.md`, `index.md` and
`log.md` have never been synced. Power loss itself is not simulated. The test proves the missing ordering,
not the torn result.

## Weakened-assertion audit

- `git diff --name-status 74129f5 021e60c -- tests` lists only additions: seven `tests/review1_*.py` files
  and `tests/test_review1_crash_consistency.py`. No existing test was modified or deleted, and nothing was
  skipped or xfailed. The `e4f4446..021e60c` range has no test changes.
- `tests/test_review1_crash_consistency.py` tests each of the six CHANGELOG `[Unreleased] ### Fixed` claims
  with real assertions:
  - Argus: tests at :57 and :72, plus savepoint nesting at :97.
  - First open: tests at :120 and :140.
  - Scrub debt: tests at :166, :181 and :194.
  - `synchronous = FULL`: test at :210.
  - Key file: tests at :222, :239 and :247.
  - OKF leftovers: tests at :271 and :292.

  Coverage stops at the happy edge of each claim. Nothing covers a resumed scrub that fails (R2-1), a
  concurrent erasure during a scrub (R2-2), a kill after the key-file link (R2-6), or two outputs whose
  names collide by suffix (R2-3). `test_file_vault_commits_are_fsynced` (:210-216) checks `>= 2`, which also
  accepts EXTRA (3). That is fine, and it is not a weakening.
