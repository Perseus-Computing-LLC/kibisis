## Findings

### R2-F1 (high) `put_batch` drops a `MemoryEntity` item's origin: a model-origin entity replaces a person's reviewed entry and is stored as the person's

Test: `tests/review2_put_batch_entity_origin_dropped.py` (2 failed, 2 passed on this head).

- `src/kibisis/vault.py:2389-2400`: for a `MemoryEntity` item, `put_batch` calls `self.put(...)` with
  category, key, content, metadata, epistemic_state, valid_from, valid_until, scope and the fence. It never
  passes `item.origin`. `source_ref` and `confidence` are dropped as well. The dict branch (`:2401-2402`)
  forwards every key, `origin` included. `MemoryEntity` has an `origin` field (`models.py`), and the signature
  accepts these items (`vault.py:2364`, `protocols.py:118-124`).
- `put` treats a missing origin as the caller vouching. On a new key it stores origin `unknown`. On a re-write it
  keeps the stored origin and class (`vault.py:2041-2042`: "A re-write that gives no origin keeps the entry's
  existing one"). A model-labelled entity therefore passes the class check as the row's own class.
- Guarantees this bypasses:
  - `put` docstring `vault.py:2035-2037`: "a lower-class writer cannot overwrite a higher-class" entry.
  - SECURITY.md:224-227 (agent-side writer, "In scope, enforced"): "A capped write cannot replace an entry a
    person verified or reviewed".
- Observed on this head. The `notes:pref` row was written with `origin="user"` and has a person's review.
  - `put(origin="model")` and a dict item with `origin="model"` are both refused (`OriginClassError`).
  - `put_batch([MemoryEntity(origin="model", ...)])` is accepted. The content becomes the model's text,
    `human_reviews` goes from 1 to 0, the attestations are gone and the version is bumped.
  - The row still says `origin="user"` / `origin_class="principal"`. A model's claim now reads as the person's
    and can only be removed by a person.
  - On a new key the same entity is stored as origin `unknown` (`external` class), not `model`.
- This is not R1 DQ3. DQ3 is the documented gap that `tool` origin carries no trust ceiling. Here the caller labelled
  the item `model`, and the label is discarded before `put` sees it.
- A realistic caller hits it by relaying entities (e.g. `dst.put_batch(src.list_entities(...))`, or model output
  parsed into `MemoryEntity`).
- Python fix: `src/kibisis/vault.py:2390-2400`. Pass `origin=item.origin` (and `source_ref`, `confidence`) to `put`.
  `MemoryEntity.origin` defaults to `"unknown"` (`models.py:60-63`). A fixer who wants origin-less entities to keep
  their current behaviour can forward the origin only when it is not that default; the test asks only that an
  explicit `model` is honoured. `tests/test_benchmark_ergonomics.py:51-67` writes origin-less entities to new keys,
  which are stored as `unknown` today as well, so it is unaffected.

### R2-F2 (high) A vault object opened before a pinning open raised the file's quorum still mints `verified` below it

Test: `tests/review2_open_vault_ignores_raised_quorum.py` (1 failed, 2 passed on this head).

- Each vault object reads the file's stored quorum once, at open (`vault.py:1323-1385`,
  `_persist_verification_quorum`), and keeps it in `self.verification_quorum`.
- The verdict compares attestations against that in-memory value inside the review's write transaction
  (`_vault_review.py:544-548`). The author-attestation path in `_put` does the same (`vault.py:1749-1754`).
  Neither re-reads `vault_meta.verification_quorum`.
- Documented guarantees this contradicts:
  - SECURITY.md:261-265: "The quorum itself is a property of the vault file, not a per-process setting".
  - `vault.py:294-296`: "A stored quorum is a floor".
- Observed on this head, with three vault objects on one file:
  1. `early` opens. Nothing is stored yet, so it runs at the default of 2.
  2. A model-origin row is written.
  3. A pinning open (`verification_quorum=3, pin_quorum=True`) stores 3. A fresh open now adopts 3, and an open
     asking for less is refused.
  4. Two people approve through `early`. The row is stored `verified` with attestations `['alice', 'bob']` and
     `quorum_at_verification` 2, which every later open reads as verified.
- Controls:
  - Two approvals verify before any raise.
  - A vault opened after the raise needs three.
- This is a stale-reader / reordered-call laundering. A long-lived embedder (`trust_caller_identity=True`) keeps
  verifying below a raised quorum until it restarts, in the same way that a lease holder kept writing under a
  superseded token. Attestations come from `attester=`, so the result does not depend on the host account.
- Python fix: re-read the file's quorum inside the write transaction and verify against
  `max(self.verification_quorum, stored)`. That applies at `_vault_review.py:539-550` and `vault.py:1745-1756`; the
  read is `self._stored_quorum()`, `vault.py:1235`.

### R2-F3 (medium) okf `import_bundle` decides conflicts on a stale read; a row archived in between is revived

Test: `tests/review2_okf_import_stale_conflict_check.py` (1 failed, 2 passed on this head).

- `src/kibisis/okf/importer.py:449-450` reads every row once (`vault.list_entities(...)`) before the loop.
- `:481` runs `_row_conflict(vault, row, c.body)` against that stale `row`. The conflicts that only the
  importer enforces are `archived`, `confidential`/`sensitivity`, `pending_review` and `disputed`
  (`:369-391`; module docstring `:39-51`: "the write would revive the row", "writes the vault would accept but
  a person decides").
- `:489` → `_write` (`:398-425`) then calls `vault.put(..., origin="model")` in a separate transaction. The
  metadata it passes is also built from the stale row (`:408-409`).
- Nothing re-reads the row or holds the write lock between the check and the put. A person's archive on
  another connection (or a cascade/contradiction dispute, or a supersession proposal) that commits after the scan
  is therefore overwritten. The import writes the row the docstring says it never sends to the vault:
  `put` revives the archived row and replaces its content with the bundle's model text.
- The vault's own refusals (`superseded`, `origin_class`, `reviewed`, `tombstoned`) are re-checked atomically
  inside `put`, so a person's *review* is safe. Only the importer-level conflicts above are exposed.
- Same class as round-1 F1 (check and write in separate transactions), on the OKF path.
- Test construction: two `SQLiteMemoryVault` objects on one file. The agent's `list_entities` is wrapped so that
  the person's `archive` commits right after the importer's scan. Expected: row still archived, content
  unchanged, nothing written. On head the row comes back unarchived with the edited model body and
  `report.written == ['default/decision/bound.md']`.
- Controls: an archive before the import is reported as conflict `archived`. Without the archive, the import
  rewrites the row.
- Severity medium, not high: the protections at stake are importer conventions (module docstring), not
  SECURITY.md guarantees, and "Live use in P13 is dry-run only" (`:54`).
- Python fix: `src/kibisis/okf/importer.py:456-492`. For each concept, re-read the row and run `_row_conflict`
  inside `vault._write_tx()` together with `_write`, so the check and the put share one transaction. The
  vault's `put` joins it.

## Design questions (no test filed)

1. **Restoring the vault's own older snapshot erases a later `disputed` verdict and the disputer's review record.**
   - Probe: a keyed vault opened with `trust_caller_identity=True`; a model-origin entry reaches `verified` on
     alice's and bob's approvals; `export_snapshot()`; carol disputes it (`disputed`, three review records);
     `import_snapshot(own snapshot)`.
   - The entry comes back `verified` with attestations `['alice', 'bob']` and two review records. Carol's dispute
     leaves no trace on the entry.
   - This is the documented point-in-time replay (`_vault_snapshot.py:266-269`, SECURITY.md:318-321: "over any
     review made since (a later rejection still wins, because tombstones are never removed)"), so no test is
     filed. The owner may want a later `disputed` verdict to survive a restore the way a rejection does.
     As it stands, a restore re-launders an entry a person disputed back to `verified`.
2. **`put_batch` is atomic only inside a caller's transaction, and `with self._conn:` (`vault.py:2387`) commits
   that caller's transaction.**
   - Standalone, each item is its own transaction. The docstring (`vault.py:2371-2373`) says so: "the items
     before it stay written".
   - Inside an enclosing `_write_tx` (`AMLService.add`, `aml_adapter.py:520-523`), the sqlite3 context manager
     commits or rolls back the outer transaction when the batch ends.
   - `AMLService.add` calls `put_batch` last, and the marker is the batch's last item, so the request still
     lands whole or not at all.
   - Any future caller that writes after `put_batch` in the same `_write_tx` would silently lose both atomicity
     and the write lock.
3. **R1 DQ2 also reaches entries a person reviewed (not re-filed).**
   - Probe: two keyed vaults under different passphrases, so the snapshot is foreign and its seal does not open.
     In the importer, a principal entry carries one person's `verified` review. The foreign snapshot has a row
     with `origin: "user"`. `import_snapshot(snap, origin="model")` without `clear_existing` restores it.
   - The person's entry is replaced: new content, `candidate`, zero review records, origin still `user`.
   - The `import_snapshot` docstring (`_vault_snapshot.py:263-266`) says a restore "leaves a live entry a person
     reviewed ... in place when the snapshot is not this vault's". That protection only works through `put`'s
     `ReviewedEntryError`, which a principal-class row never triggers, and the row's class comes from the file's
     uncapped origin (DQ2).
   - R1 DQ2 cites these same lines and SECURITY.md:314-316 ("a snapshot file is a trusted input for content") as
     the documented behaviour, so I treat it as covered by the owner's decision. The docstring's "a person
     reviewed" clause and the code disagree, and the owner may want an explicit `_is_reviewed` check on a
     foreign restore independent of the row's class.

## Checked and clean

- **Round-1 fix seams.** A refusal-equivalence probe was re-run fresh before finishing: 15 scenarios × 3 modes.
  - Modes: unfenced with no token; `enforce_fencing=True` with the current token; unfenced with the current token
    passed.
  - Refusals:
    - `put` and dict `put_batch` with `origin="model"` over a person-reviewed entry → `OriginClassError`.
    - `tombstone`, `purge` and `archive` by `model` of that entry, and `set_persona_slot(origin="model")` over
      the person's slot → `ReviewedEntryError`.
    - `lift_tombstone` by `model`, and a model-origin reviewer → `PermissionError`.
    - A bad verdict → `ValueError`; a missing entry → `KeyError`.
  - Calls that are accepted by design: a put of new content on a tombstoned key, a model `supersede` proposal,
    a foreign import with and without `clear_existing`, and `admit_candidate` over a reviewed key.
  - Exception type, entity rows and the new journal rows (action, key, reason) were identical in all three modes
    for 15/15.
  - `_fence_first` (`vault.py:891-909`) is a no-op when the fence does not apply (`:904-906`). Otherwise it opens
    `_write_tx` and checks the fence before the block (`:907-909`). A nested `_write_tx` joins the open
    transaction (`:927-929`), so `admit` → `review_entity` stays one transaction.
  - The line-458 review transaction already existed at the base (`_vault_review.py:453` at 74129f58ad45).
- **Fenced-out writes.** A fence-matrix probe was re-run fresh: 14 call shapes × 6 fence variants on a
  `FileLeaseCoordinator`.
  - Call shapes: put, store, dict put_batch, supersede, admit_candidate, archive, purge, tombstone,
    lift_tombstone, review_entity `verified` and `disputed`, set_persona_slot, import_snapshot, and
    import_snapshot with `clear_existing`.
  - Variants:
    - the token of a released and re-acquired lease;
    - another holder;
    - another resource;
    - no token on an `enforce_fencing` vault;
    - the token of a released lease;
    - a stale token without `holder_id`.
  - Result: 84/84 raised `LeaseConflictError` with entity rows and journal-row count unchanged. The current token
    was accepted for 14/14.
  - `admit` was not driven by this probe (a command-text guard on this host). `tests/test_fence_first_refusals.py:81-82`
    covers its fenced-out refusal.
- **`AMLService.add` replay** (`aml_adapter.py:500-528`, code reading). The marker read, the 409 check and
  `put_batch` share one `_write_tx`. The marker is the batch's last item, so messages and marker land together.
  An identical retry is a no-op and a different payload under the same id is 409.
- **Lease expiry/renew/release ordering.** Covered by the native probe under "Rust-only" above.
- **OKF import refusals enforced by the vault.** `superseded`, `origin_class`, `reviewed` and `tombstoned` are
  re-checked inside `put`'s transaction, so only importer-level conflicts are exposed (R2-F3).
- **Search-index writes.** They are maintenance writes of derived data (`_vault_search.py:954,997,1129,1134`), not
  entity writes.
